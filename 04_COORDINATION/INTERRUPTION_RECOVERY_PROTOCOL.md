# پروتکل تاب‌آوری در برابر قطع اینترنت، توقف چت و ابهام عملیات

این سند مکمل START_HERE، MASTER-00، WORKER_PROTOCOL و LOCK_MANAGER_PROTOCOL است و برای همه حساب‌ها، چت‌ها، عامل‌ها و پرامپت‌ها لازم‌الاجراست.

## اصل بنیادین
حافظه چت، خلاصه خودکار، پاسخ ابزار یا تصور عامل منبع حقیقت نیست. فقط وضعیت قابل بازیابی از GitHub معتبر است. هیچ عملیات نوشتنی نباید به ادامه همان نشست وابسته باشد.

## شناسه‌های پایدار و تکرار امن
- هر کار یک TASK_ID پایدار دارد؛ هر نشست/اجرای مجدد RUN_ID جداگانه دارد.
- هر اقدام تغییردهنده باید OPERATION_ID پایدار و یکتا داشته باشد؛ برای retry همان اقدام، همان OPERATION_ID حفظ شود.
- قبل از ساخت Issue، branch، PR، commit یا فایل، وجود اثر قبلی را با TASK_ID، RUN_ID، OPERATION_ID، نام branch، مسیر فایل و commit جست‌وجو کن.
- ایجاد تکراری ممنوع است. اگر نتیجه درخواست قبلی مبهم است، ابتدا وضعیت GitHub را بخوان؛ کورکورانه همان درخواست را دوباره نفرست.
- اگر عملیات قبلی انجام شده، اثر موجود را اعتبارسنجی و ادامه بده. اگر انجام نشده، همان عملیات را با همان شناسه و ورودی تکرار کن. اگر بخشی انجام شده، فقط بخش باقی‌مانده را اجرا کن.
- برای Issue/PR از شناسه و لینک موجود استفاده کن؛ برای branch از نام پایدار TASK؛ برای فایل از مسیر ثابت و بررسی SHA؛ برای قفل فقط از فرمان‌های `/farast claim/heartbeat/release` و fencing token صادرشده توسط coordinator استفاده کن؛ direct-CAS worker ممنوع است.

## پروتکل قطع اتصال یا timeout
پس از قطع اینترنت، timeout، خطای ابزار، بسته‌شدن تب، توقف مدل یا پاسخ نامشخص:
1. تمام نوشتن‌ها را متوقف کن؛ نتیجه آخرین عملیات را موفق یا ناموفق فرض نکن.
2. نشست جدید را فقط با TASK_ID/لینک Issue/PR/branch/checkpoint بازیابی کن؛ اگر در خلاصه خودکار موجود نبود، GitHub را با شناسه‌های پایدار جست‌وجو کن.
3. آخرین commit و head شاخه، Issue، PR، فایل‌های تغییرکرده، آخرین checkpoint، شواهد و رجیستری قفل را دوباره بخوان.
4. عملیات ناتمام را با مقایسه وضعیت واقعی GitHub و OPERATION_ID تشخیص بده.
5. اگر عملیات ثبت شده است، آن را تکرار نکن؛ اگر ثبت نشده، پس از بررسی مالکیت و قفل، ادامه بده.
6. اگر نمی‌توانی نتیجه را قطعی کنی، وضعیت را AMBIGUOUS/BLOCKED ثبت کن و از ایجاد اثر دوم خودداری کن.
7. پس از بازیابی، checkpoint تازه با زمان UTC و مرجع commit بنویس.

## قطع در میانه عملیات چندمرحله‌ای
- مراحل را به گام‌های کوچک و قابل بازیابی تقسیم کن؛ هر گام باید ورودی، خروجی، شناسه عملیات و معیار تأیید داشته باشد.
- پیش از اقدام پرریسک و پس از هر گام پایدار، checkpoint ثبت کن.
- برای تغییرات چندفایلی، تا حد امکان یک commit اتمیک بساز؛ از وضعیت نیمه‌کاره روی شاخه اصلی اجتناب کن.
- اگر چند commit جدا لازم است، manifest پیشرفت مشخص کند کدام commitها ثبت شده‌اند و کدام گام‌ها باقی‌اند.
- عملیات برگشت‌ناپذیر، انتشار، migration مخرب، حذف، تغییر مجوز، هزینه و ادغام بدون approval صریح انجام نشود.
- در conflict، force-push یا بازنویسی تاریخچه ممنوع؛ ابتدا head جدید را بخوان، تغییرات دیگران را حفظ و با روش امن ادغام کن.

## پرشدن پنجره زمینه و خلاصه خودکار
- فرض کن چت ممکن است هر لحظه به‌علت پرشدن context بسته یا به چت جدید منتقل شود.
- پیش از رسیدن به محدودیت زمینه، checkpoint را در GitHub ثبت کن؛ منتظر هشدار یا خلاصه خودکار نمان.
- checkpoint باید آن‌قدر مستقل باشد که عامل ناآشنا بدون متن چت بتواند ادامه دهد: هدف، دامنه، TASK_ID، آخرین گام قطعی، گام ناتمام، branch، commit SHA، فایل‌ها، شواهد، خطاها، تصمیم‌های لازم، قفل‌ها و دستور دقیق اقدام بعدی.
- خلاصه خودکار چت فقط سرنخ است؛ هر ادعا را با GitHub تطبیق بده. اگر خلاصه با GitHub تعارض داشت، GitHub مقدم است.
- هیچ داده ضروری، تصمیم، بازخورد یا نتیجه آزمونی را فقط در چت نگه ندار.
- اگر زمان/زمینه محدود است، کار جدید شروع نکن؛ اول checkpoint و handoff قابل بازیابی بساز.

## تداوم مالکیت و قفل
- پس از وقفه، RUN_ID جدید بساز ولی TASK_ID و branch وظیفه را حفظ کن، مگر branch حذف/نامعتبر شده باشد.
- lock قبلی را فقط پس از خواندن رجیستری زنده و تطبیق TASK_ID/RUN_ID/fencing_token معتبر بدان.
- lease منقضی، token قدیمی، workflow ناموفق یا پاسخ نامعلوم = توقف نوشتن؛ پس از انقضا claim جدید را فقط از مسیر coordinator بگیر.
- هیچ عامل جدیدی lock یا branch عامل دیگر را تصاحب نکند مگر مالکیت طبق پروتکل رسماً منقضی/آزاد شده باشد.
- قفل رجیسترهای مشترک و سیاست single-writer برقرار می‌ماند؛ checkpoint جایگزین قفل نیست.

## سطح‌بندی نتیجه
- CONFIRMED: اثر در GitHub مشاهده و با SHA/شناسه تأیید شده.
- NOT_APPLIED: پس از بررسی منبع حقیقت، اثر ایجاد نشده است.
- PARTIAL: فقط بخشی از مراحل پایدار شده و بخش باقی‌مانده مشخص است.
- AMBIGUOUS: شواهد برای تعیین نتیجه کافی نیست؛ هیچ retry نوشتنی انجام نده.
- BLOCKED: دسترسی، مالکیت، قفل یا approval مانع ادامه است.

## چک‌لیست بازیابی سریع
1. مخزن و visibility/access را تأیید کن.
2. TASK_ID و Issue موجود را پیدا کن.
3. branch و آخرین commit SHA را بخوان.
4. checkpoint و آخرین OPERATION_ID را بخوان.
5. PRها، CI، reviewها و تغییرات دیگران را بررسی کن.
6. رجیستری قفل و lease/fencing token را بررسی کن.
7. آخرین گام تأییدشده را تکرار نکن.
8. دقیقاً از NEXT_ACTION ادامه بده.
9. checkpoint و شواهد را به‌روز کن.
10. فقط پس از تأیید نهایی، قفل متعلق به خود را آزاد کن.

## محدودیت تضمین
GitHub می‌تواند تاریخچه و وضعیت پایدار را نگه دارد، اما دسترسی هر حساب، ابزار یا عامل و اجرای خودکار heartbeat را تضمین نمی‌کند. اگر دسترسی read/write یا workflow coordinator در حساب/مخزن جدید موجود نیست، فقط read-only انجام بده و هیچ موفقیت نوشتنی ادعا نکن. آزمون واقعی دو حساب مستقل پیش‌شرط اتکای تیمی به قفل است.
