# پروتکل قفل و مالکیت منابع — محدودیت‌های صادقانه

## واقعیت فنی
GitHub Issues و labels به‌تنهایی قفل اتمیک منابع نیستند. GitHub Actions concurrency نیز صف دائمی/قفل توزیع‌شده با FIFO تضمین‌شده نیست. این مخزن در نسخه اولیه سرویس lock مستقل یا GitHub App اختصاصی ندارد. بنابراین این پروتکل فعلاً **قفل تعاونی (cooperative lease)** است، نه تضمین رمزنگارانه/اتمیک. عامل حق ندارد آن را hard lock معرفی کند.

## روش اجرایی فعلی
1. قبل از claim، Issueها و PRهای باز و فایل‌های تغییر یافته آن‌ها را بررسی کن.
2. در TASK Issue فهرست دقیق `RESOURCE_KEYS` را بنویس: مانند `module:payments`, `file:app/...`, `schema:orders`, `contract:payment-callback`.
3. یک Issue قفل با عنوان `LOCK: <resource-key>` یا یک کامنت claim در TASK ایجاد/ثبت کن و لینک آن را به وظیفه پیوند بده.
4. اگر قفل باز و متعلق به عامل دیگر است، وارد تغییر نوشتنی نشو؛ کار خواندنی/مستقل را ادامه بده.
5. Lease پیشنهادی 30 دقیقه بدون heartbeat و حداکثر 4 ساعت است؛ این زمان سیاست عملیاتی اولیه است، نه ویژگی تضمین‌شده GitHub. زمان UTC و heartbeat را ثبت کن.
6. آزادسازی فقط با کامنت RELEASE و وضعیت نهایی، یا پس از بررسی انقضا و اطمینان از نبود فعالیت معتبر.
7. قفل مبهم/متناقض = STOP WRITES؛ مالکیت را جعل نکن.

## ایمنی تغییر
- هر عامل branch اختصاصی `work/<TASK_ID>-<slug>` دارد.
- PR اجباری به main؛ هرگز commit مستقیم main.
- فایل‌های مشترک کنترل‌پلین فقط با PR و بررسی تداخل تغییر می‌کنند.
- در صورت امکان از تغییرات کوچک و فایل‌های مجزا استفاده شود.
- ادغام نهایی و تغییرات حساس فقط با تأیید مالک/بازبین مجاز.
- در repo محصول، همین قواعد سخت‌گیرانه‌تر اجرا شوند.

## مسیر ارتقای قفل سخت
برای تضمین اتمیک واقعی، یک سرویس lock با عملیات compare-and-swap، lease و fencing token لازم است؛ می‌تواند GitHub App/backend اختصاصی یا پایگاه داده تراکنشی با API باشد. تا وقتی ساخته و با آزمون رقابت‌پذیری اثبات نشده، قفل تعاونی تنها کنترل کاهش ریسک است.
