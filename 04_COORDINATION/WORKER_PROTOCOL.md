# پروتکل عامل‌ها و همکاران

> قرارداد نوشتن جاری: پیش از هر write فرمان /farast claim را از طریق Issue اجرا کن؛ workflow مرکزی تنها نویسنده رجیستری قفل است. workerها مجاز به direct-CAS یا تغییر مستقیم ACTIVE_LOCKS.json نیستند. جزئیات و قالب فرمان‌ها در COORDINATOR_COMMANDS.md است. اگر workflow فعال نیست/پاسخ معتبر ندارد، STOP WRITES.

## هویت اجرا
هر اجرا این فیلدها را در Issue/checkpoint ثبت می‌کند: TASK_ID، PROMPT_ID، RUN_ID یکتا، نام مستعار عامل، حساب/چت به‌صورت اختیاری، branch، commit SHA، زمان شروع/پایان UTC، وضعیت.

هویت چت صرفاً ادعای عامل است؛ GitHub هویت واقعی مکالمه ChatGPT را اثبات نمی‌کند. توکن یا اطلاعات حساب در گزارش ممنوع است.

## چرخه وظیفه
DISCOVER → DEDUPLICATE → CLAIM → PLAN → EXECUTE → CHECKPOINT → REVIEW → HANDOFF → CLOSE.

## قواعد موازی‌کاری
- کارهای خواندنی می‌توانند موازی باشند.
- کارهای نوشتنی فقط در branch اختصاصی همان RUN و با منابع اعلام‌شده.
- اگر دو کار یک فایل، ماژول، schema، API contract یا تصمیم مشترک را تغییر می‌دهند، باید یکی منتظر بماند یا دامنه تغییر را تفکیک کند.
- همه تغییرات از PR عبور می‌کنند؛ تغییر مستقیم main ممنوع.
- تغییرات هم‌زمان در یک مسیر ممکن است conflict ایجاد کند؛ conflict را با ادغام کور حل نکن.
- عامل باید PRهای باز و issueهای IN_PROGRESS را جست‌وجو کند.

## استقلال و زمان‌بندی
هیچ PR یا TASK شماره‌ای تقدم زمانی ندارد. فقط وابستگی واقعی و Gate مانع شروع است. وظایف مستقل قابل اجرا هستند. اگر پیش‌نیاز ناقص است، بخش مستقل را انجام بده و مانع را ثبت کن.

## ارتباط با مالک
سؤال فقط برای تصمیم/داده حیاتی که در هیچ منبعی موجود نیست. حداکثر یک سؤال دقیق در یک نوبت. در غیر این صورت UNKNOWN ثبت و ادامه امن انجام شود. گزارش مکالمه‌ای مفصل ممنوع؛ گزارش در GitHub.

## بازیابی
در شروع مجدد:
1. TASK_ID را از ورودی/Issue بازیابی کن.
2. آخرین Issue body/comment و checkpoint را بخوان.
3. branch و آخرین commit را بررسی کن.
4. شواهد و خروجی موجود را اعتبارسنجی کن.
5. موارد انجام‌شده را تکرار نکن.
6. مالکیت منقضی/نامعلوم را دوباره درخواست کن.
7. از آخرین اقدام ناتمام ادامه بده.
اگر TASK_ID داده نشده، جست‌وجوی مشابه انجام بده؛ وظیفه موجود را پیدا کن و از ساخت duplicate پرهیز کن.

## تعریف پایان
هر وظیفه باید خروجی، معیار پذیرش، شواهد، تست‌ها، ریسک باقی‌مانده، وضعیت تأیید انسانی و لینک PR/commit داشته باشد. DONE_VERIFIED فقط با شواهد و تأیید لازم.


## مالکیت تک‌نویسنده‌ای رجیسترهای مرکزی
برای حفظ اجرای موازی، هر عامل نباید هم‌زمان فایل‌های وضعیت کلان را ویرایش کند:
- GitHub Issues منبع اصلی وضعیت هر TASK هستند؛ `TASK_INDEX.md` نمای تجمیعی است.
- `MASTER_STATUS.md` و `GOAL_STATUS.csv` فقط توسط Status Steward/عامل هماهنگ‌کننده به‌روزرسانی شوند.
- `USER_FEEDBACK_REGISTER.md` فقط توسط Feedback Steward/عامل دریافت بازخورد.
- `DECISION_REGISTER.md` فقط توسط Decision Steward پس از ثبت approval.
- `EXP_STAGE_LEDGER.csv`، `CAPABILITY_REGISTER.csv` و `REQUIREMENTS_TRACEABILITY.csv` فقط توسط TASK مالک همان رجیستر یا steward تعیین‌شده.
- عامل‌های دیگر گزارش اختصاصی TASK، checkpoint و Issue خود را بنویسند و پیشنهاد تغییر رجیستر مرکزی را در PR جدا ارائه کنند.
- اگر نقش steward مشخص نیست، رجیستر مرکزی را تغییر نده؛ فقط خروجی اختصاصی بساز و handoff کن.
- هر نوشتن در رجیستر مرکزی نیازمند RESOURCE_KEY دقیق و قفل CAS تا ثبت commit/PR است. PRهای متعارض باید پیش از merge هماهنگ شوند.
